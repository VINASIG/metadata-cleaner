# Web design, responsive and accessibility

## Sources and adoption

WEB-001 MUST use the VINASIG web-design-system for tokens/components and vinasig-brand-assets for supplied artwork. Pin references in the project's asset/source record. Do not fork a competing design system, invent approved values, redraw VINASIG artwork, or grant its rights. The design system currently labels proposals as drafts. Adopt a proposal explicitly for a product and record that choice. The task already settles font and icon roles.

The owner approved transparent website header logos on 4 October 2026. Use an unchanged horizontal export on the actual header surface. Choose Primary Color, Color Black or Monochrome Black for a light surface, and Reversed or Monochrome White for a dark surface. A light-only website keeps its light variant even when the operating system requests dark mode. A consistently dark sidebar keeps its dark variant. Theme-aware surfaces must select the matching asset before JavaScript runs.

Do not add a white panel, padded or rounded card, border frame, shadow, filter or cropped corners to the header logo. Keep the supplied aspect ratio, accessible link name and internal artwork, including intentional white geometry. Place layout spacing around the link and give it a usable target of at least 44 by 44 CSS px independently of the artwork's display size. Do not reconstruct the wordmark with live text. The contained mark is an existing square avatar asset, not the default website header. Any unavoidable background exception needs an owner-approved reason and a review date.

On VINASIG-owned websites the header or sidebar VINASIG logo is a native link to `https://vinasig.io.vn/`, with a localized name identifying the VINASIG homepage. Keep project navigation and GitHub source links separate. Do not send the logo to the GitHub organization, a project homepage or the current locale route. Run `inspectHeaderBrand` on initial HTML and enhanced light/dark states, including focus and hover, and exercise the link at narrow and desktop widths. Verify the published page after deployment as well as the local build.

- Space Grotesk is the sole named UI typeface, served locally with its OFL notice. Check Vietnamese glyphs, 300-700 weight support, font loading and fallback. A technical code block may use a documented platform monospace fallback for legibility. It does not change the UI font.
- Lucide supplies interface SVG icons. Keep consistent size/stroke, import only used icons and name controls accessibly. Decorative SVGs stay out of the accessibility tree.
- Simple Icons supplies third-party brand marks where appropriate. Library licensing does not waive brand rules. Prefer currentColor unless the context requires brand color. Provider sign-in buttons follow the provider's approved artwork and requirements. VINASIG artwork comes from its own archive.
- Read the design system's element catalog, specimen and component guidance for the control being built. Preserve control type/behavior in references. Check both closed and open dropdown panels.

WEB-002 SHOULD use the current Bright Playful Minimalism proposal when the consuming project adopts it. Keep flat content-led structure, neutral surfaces, measured type, clear spacing and purposeful identity accents. Preserve semantic tokens and identity anchors. Avoid default gradients, oversized hero text, empty card grids, decorative badges and ornamental illustrations. Do not copy Apple's whole visual identity to obtain subtle motion. The source typography and spacing values remain in the design-system repository, not a duplicated token library here.

WEB-003 MUST keep essential content accessible, use semantic HTML and native controls when suitable, correct roles/names/states, form labels, visible focus, descriptive links and a working favicon across deployment base paths. Content and control usefulness decide visible UI elements; implementation badges and machine indexes are not mandatory product chrome. Inspect light/dark if supported.

WEB-008 MUST style the complete control using the consuming project's tokens and Space Grotesk. This includes the open dropdown/listbox, calendar, color chooser, slider track/thumb and relevant disabled, invalid, focus and selected states. Styling only the closed native select or adding `accent-color` to an operating-system popup does not meet this requirement. Do not depend on operating-system select, date/time or color popups for the intended VINASIG interface. Prefer an existing reviewed design-system control. A native input may retain semantics under a custom presentation. A range input may retain native keyboard behavior when its track and thumb are styled across supported engines.

Custom controls must retain labels, keyboard behavior, focus restoration, touch usability, form values, reset/disabled behavior and readable selected states. Keep direct text entry where dates, times, colors or numbers benefit from it. Fit open panels within the viewport without clipping the page. Test both closed and open controls in supported engines, light/dark themes, narrow viewports and enlarged text. Do not add a UI library or remove useful input behavior merely to satisfy styling. Browser dialogs for file selection, printing and downloads remain platform interactions.

Before implementation, inventory native and custom controls from both source and rendered routes, including controls revealed by tabs, disclosures, content-type changes or dialogs. Cover single/multiple select, autocomplete/datalist, date/time/month/week, color/alpha/hue, range, number steppers, search clear buttons, checkbox/radio/switch, file-input triggers, progress/meter, disclosure indicators, textarea resize affordances and scrollbars inside every popup or scrollable region. Record absent controls as NOT_APPLICABLE rather than adding product features. A CSS reset, `appearance: none`, `accent-color` or a custom closed trigger alone does not prove the complete control is styled.

Use `web-design-system/src/styles/control-surfaces.css` for shared native presentation and the reviewed range/select/date implementations for behavior. Skin checkbox/radio checked, mixed, disabled, invalid and focus states. Skin both track and value of progress/meter in each supported engine. Skin native subparts without deleting working clear, step, resize or upload actions. Inspect options, selection indicator, internal padding, scroll track/thumb, corners and buttons in opened panels. Keep scrolling operable by wheel, keyboard, touch and thumb drag where supported, including the last option in a long list. Do not replace working native scrolling with a simulated scroll mechanism merely for its appearance.

For scrollbars use semantic theme colors, preserve contrast and keep a usable visible thumb. Provide the CSS Scrollbars standard plus an older-engine fallback where needed. Non-auto `scrollbar-color` takes precedence over `::-webkit-scrollbar` styling in modern engines. Test the actual supported engine rather than claiming pseudo-element declarations took effect. Preserve platform high-contrast rendering under forced colors. This accessibility fallback is distinct from leaving the ordinary interface unstyled.

Run `inspectControlSurfaces` alongside `inspectInterface` and `inspectControlIndicators` on initial and enhanced HTML, every applicable opened state, long scrolled panels and both themes/locales. The gate checks native control appearance, authored range/progress parts, scrollbars, disclosure indicators and expanded popup geometry/surfaces. It is structural evidence and does not certify visuals, keyboard behavior or assistive technology support. Consumer tests must assert a nonzero expected control count, open real controls, reach the final choice, confirm selection/reset/disabled/error behavior, capture AND open screenshots and verify the deployed page. Preserve intentionally compact platform-reference specimen metrics while styling their web implementation.

Render a styled, meaningful initial control in HTML. Attach its handlers before enabling it. Delayed, blocked or disabled JavaScript must not expose an operating-system popup or an apparently usable control without its handler. Retain working direct entry where available, and test the initial response as well as the enhanced interface.

For ordinary VINASIG form dropdowns, reserve at least 16 CSS px between the indicator's SVG box and the inner trailing border, and at least 12 CSS px between its box and the selected-value box. Reuse spacing tokens and logical inline-end padding. Keep the indicator at its declared dimensions without flex shrinking, text overlap or clipping. Check the actual computed geometry rather than assuming that padding or `space-between` provides it. Initial HTML and the enhanced control must keep the same spacing. Compact platform-reference specimens retain their documented platform metrics and must not be used as the ordinary form baseline.

Mark the selected value with `data-control-value` and its SVG with `data-control-indicator` in ordinary `.select-control` triggers. Run `inspectControlIndicators` from `templates/web/interface.mjs` on initial, open, selected and script-unavailable states. The guard measures visible marked controls, including disabled controls, and checks missing markers, trailing inset, value gap, declared icon size and clipping. Test long selected labels, 200% text sizing, all supported locales/themes, narrow layouts and actual breakpoint neighbors. Open before/after screenshots at a useful scale. Passing accessibility or page-overflow checks alone does not establish correct control spacing.

A labelled selection card may use its border/background as the single visible radio presentation. Retain the native input's accessibility and keyboard behavior, with a visible focus outline and selected state in forced colors. Do not duplicate a circle inside an already selected card. Declare these cards in the WEB-010 inventory and inspect their native semantics, real gaps and distinguishable selected presentation. A transparent input is not an exemption from selection-state verification.

## Shared website header and footer

WEB-009 MUST reuse the owner-approved shared header and footer contract for every new or changed VINASIG-owned website. Read the [project-start checklist](../templates/web/site-chrome.md) before creating a layout. Use the reviewed source in `web-design-system/src/styles/site-chrome.css` and `src/components/SiteFooter.astro`, or equivalent semantic HTML with the same CSS for a project without Astro. Record the reviewed source revision and compare it with the published VINASIG websites. Do not invent a separate header/footer or add a framework for this presentation.

The identity row contains one original transparent 132 CSS px horizontal logo linked to `https://vinasig.io.vn/`, then the appearance button and reciprocal language link aligned at the right. Each control has a 44 px target, the group has a 4 px gap, and Lucide Sun/Moon icons are 20 px. Product navigation belongs in a separate row or sidebar. Keep the controls beside the logo at 320 px and enlarged text. Use 32 px outer gutters/top spacing on wide screens and 16 px up to the reviewed 760 px breakpoint. Follow the product's content width rather than widening a focused tool.

The footer starts with a VINASIG homepage link followed by localized Source code, Report an issue and Licenses links, in that order. Preserve exact-revision source destinations where supported and required legal notices. Additional useful product links may follow. Reuse the border, spacing and wrapping in the shared CSS. Do not add a repeated slogan, logo tile, guessed copyright ownership or decorative badge.

Mark the identity header and footer with `data-site-header` and `data-site-footer`. Run `inspectSiteChrome` from the local web template and assert one of each. Add actual route/locale/theme, keyboard, no-JavaScript, link-destination and 200% text regressions. Check every route using a changed layout, breakpoint neighbors and all supported engines. Capture AND open screenshots of both the top and bottom of the fully scrolled page, then verify the deployed revision. Automated geometry cannot certify appearance. Exceptions need a specific owner-approved reason and review date. The general design-system draft remains a draft outside these approved requirements.

Preserve the reviewed icon artwork and target-state action. Light appearance offers the Moon icon and a localized switch-to-dark name. Dark appearance offers the Sun icon and a switch-to-light name. Test the visible SVG, accessible name, pressed state, persistence, system preference and script-unavailable state. Do not replace these with a combined SunMoon icon, emoji, a different icon family or a reversed action. Compare the exact shared CSS and original logo bytes, not just their filenames or similar appearance.

## Interface completion gate

WEB-011 MUST implement the owner-approved [shared appearance and language contract](../templates/web/shared-preferences.md) on VINASIG websites. Follow system appearance and browser language before a manual choice. Use light if system appearance cannot be read. Share only finite manual theme/language settings across HTTPS `vinasig.io.vn` subdomains, with guarded local/session fallbacks. Origin-local storage with the same key name is not ecosystem synchronization. Reuse the reviewed design-system implementation, pin its source, preserve shared chrome and prove actual cross-subdomain behavior, blocked storage and sensitive-state retention. Keep explicit locale routes accessible and do not discard active tool state when another page changes language.

WEB-010 MUST follow [the interface acceptance contract](../templates/web/ui-contract.md) for new projects and visible changes. This is the common checklist for both web profiles, including recurring defects in selection cards, icon alignment, field-local validation, slider/text bounds, inline rows, content sizing, result-action proximity, timer state, depleted tracks, visibility controls, balanced settings and natural messages. Apply it together with WEB-008 and WEB-009 rather than creating a competing project-specific standard.

Before coding, reproduce the reported state and record every applicable mode, input boundary, error, long/short result and interaction. Map each reported defect to a product regression and retained before/after evidence. Use inspectUiContract with an explicit inventory where applicable. Verify behavior independently from presentation, including elapsed time with the pointer still on Resume. Capture AND open each changed major mode and difficult state, both page ends and the affected deployed interface. Passing a broad suite in an initial mode is not evidence for untested modes. Keep automated, agent visual, independent, participant and production observations distinct. Do not declare a reported defect fixed until its mapped outcome is observed, or explicitly mark the remaining verification as NOT_RUN.

## Responsive evidence

WEB-004 MUST test representative routes/templates and shared components at 360x800, 390x844, 768x1024, 1024x768 and 1440x900. Add 320 CSS px reflow, both sides of actual content breakpoints, intermediate widths, long/localized text, enlarged text and relevant landscape. Derive breakpoints from the project, not a fixed VINASIG device list.

WEB-005 MUST scroll through the full page, capture AND open screenshots, inspect DOM/computed styles/bounds and use changed controls. Test applicable menus, overlays, form errors, loading, empty and long-content states. Fix intrinsic width, wrapping, sizing or positioning in source. Never hide page overflow, shrink the page with zoom/transform, hide content or remove functions to mask a defect. Mark genuinely intentional table/code/carousel horizontal scrolling. Automated no-overflow is one assertion, not visual approval.

WEB-006 MUST select and document a Chromium/Firefox/WebKit support matrix, run relevant engines and report NOT_RUN engines honestly. Browser emulation is not a real phone. Visual baselines need inspected images and review before acceptance. Save immutable before/after evidence under output/responsive with route, viewport and state names.

WEB-007 MUST target WCAG 2.2 AA for web. Combine axe-core with keyboard/focus and escape behavior, contrast, target usability, text enlargement/reflow and applicable assistive technology checks. An axe pass is a partial automated result. Record screen-reader/human checks separately when unavailable. The reusable Playwright helpers cover a baseline; consumer tests must add real flows and difficult states.
