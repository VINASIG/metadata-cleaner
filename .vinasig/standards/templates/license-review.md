# Project license review

Record the actual repository and revision, decision date, owner authorization and distribution paths.

## Decision

| Material and paths                       | Selected SPDX license or policy | Purpose and rationale                                |
| ---------------------------------------- | ------------------------------- | ---------------------------------------------------- |
| Software                                 | Identify the standard license.  | Explain AGPL or a justified exception.               |
| Documentation and executable examples    | Separate their grants.          | Keep knowledge shareable and code integration clear. |
| Fonts, data, marks and third-party files | State actual individual terms.  | Preserve external grants and rights.                 |

## Rights and dependencies

Record Git authors/contributors, imported material, original notices, available ownership evidence and necessary consent. State what was actually inspected. Repository control and an empty contributor list are not proof of complete title.

List runtime/build dependencies and compatibility findings. Identify selected dual-license options and distinguish separate reference archives from compiled or linked material.

## Implementation

List LICENSE, secondary texts, LICENSES.md, README, SPDX/package metadata, BRAND_POLICY.md, notices and delivery changes. Record source/version access for distributed software and applicable AGPL remote-interaction arrangements.

## Verification and remaining review

Use PASS, FAIL, NOT_RUN or NOT_APPLICABLE with commands, evidence and reasons. Include text digests, preserved assets, metadata agreement and the published revision. Report unresolved provenance, incompatible terms or future contribution changes for human review. A proposal is not a grant.
